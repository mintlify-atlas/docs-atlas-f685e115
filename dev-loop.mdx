`arc dev` is the largest command in the `arc` CLI and the one the rest of the development experience depends on. It supervises two child processes — the Rust application and Vite — watches the source tree for changes, rebuilds on every save, and proxies all browser traffic through a single TCP port so you never switch addresses between a backend change and a frontend change. This page explains what it does, how it measures rebuild time, what the flags do, and what `arc doctor` and `arc routes` offer alongside it.

## What arc dev does

When you run `arc dev` inside a project directory, the supervisor:

1. Discovers the project root and verifies the frontend's npm dependencies are installed.
2. Mints two process-private IPC endpoints — one for Vite, one for the application.
3. Writes Vite's entry script into a scratch directory and starts Vite in middleware mode.
4. Waits for Vite to listen on its endpoint (up to 30 seconds).
5. Binds the one TCP port — after Vite starts, so a port clash is reported before anything has been built.
6. Builds the application with `cargo build --features dev` and waits for it to listen.
7. Prints the URL.

From that point on, every file change triggers a rebuild that replaces only the application child. Vite's HMR socket — which is a connection through the same listener — is never dropped during a rebuild because the process that holds the port is the supervisor, not the application being replaced.

```text
browser --TCP:1183--> arc dev
                        |-- Vite's? --> vite IPC   (ARCATURE_VITE_IPC)
                        `-- otherwise -> app IPC   (ARCATURE_APP_IPC)
```

The one-port design is written up in [ADR 0003](https://github.com/ArcatureLabs/Arcature/blob/main/docs/decisions/0003-one-tcp-port.md). The short version: the process holding the port is not the process being rebuilt, so a request that arrives mid-rebuild is queued rather than refused.

## Startup output

```text
  vite    ready in 1.24s (node 20.11.0)

  Arcature 0.1.3

  Local:    http://127.0.0.1:1183
  Network:  use --host to expose
```

The URL is not printed until the first build has finished and the application is accepting connections. Opening the browser early gives you a holding page rather than a refused connection.

## Flags

| Flag | Default | Effect |
|---|---|---|
| `--port <PORT>` | `1183` | The one TCP port the supervisor binds. |
| `--host <HOST>` | `127.0.0.1` | The IP address to bind. Pass `0.0.0.0` to expose to the local network. |
| `--open` | off | Open the default browser once the first build is serving. |

<Warning>
The default bind is loopback (`127.0.0.1`). A development build with debug assertions on is not something to publish to a network by accident. Pass `--host 0.0.0.0` explicitly when you need network access.
</Warning>

If the port is already in use, `arc dev` reports it and tells you to pass `--port`:

```text
could not bind 127.0.0.1:1183: address already in use.
This is the only TCP port `arc dev` uses; pass --port to choose another one.
```

## Rebuild timing

The supervisor prints a timing line after each successful rebuild:

```text
cargo 7.85s (check 2.73s, codegen+link 5.06s)  swap 0.21s  spawn 1.44s  boot 0.31s  total 9.81s
```

| Stage | What it measures |
|---|---|
| `cargo` | `cargo build --features dev`, spawn to exit |
| `check` | Start of the build to the last non-executable artifact (type-checking) |
| `codegen+link` | That boundary to the linked executable |
| `swap` | Stopping the old process and staging the new binary |
| `spawn` | Asking the OS to start the new process |
| `boot` | The new process starting to its first accepted IPC connection |

A `.tsx`, `.vue`, or `.css` edit never reaches this loop — Vite handles those in its own HMR path without restarting the Rust process at all.

### Measured rebuild performance

The dev-loop documentation includes a measured baseline on a 4-core Windows machine with concurrent load. Reproducing the numbers on an idle developer laptop will give better results; the *shape* is what holds across machines.

| Measurement | Result |
|---|---|
| Cold build, empty `target/` | 52m 38s |
| `cargo build` with nothing to do | 4.1s |
| One-line handler change | **33–38s** (under load) / **~4.4s** (idle machine) |
| Type-check only (`cargo check`) | **~1.6s** warm |

On an otherwise idle machine, six consecutive one-line handler rebuilds measured 4.3–5.8 seconds wall clock. Type-checking a one-line change is 1.6 seconds; everything above that is code generation and linking for the whole program, which does not shrink when the diff shrinks.

The scaffold already sets the following in `Cargo.toml` to keep dependency debug information out of the application crate and cut rebuild time roughly in half:

```toml
[profile.dev.package."*"]
opt-level = 2
debug = false

[profile.dev.build-override]
opt-level = 2
debug = false
```

<Tip>
A developer who wants a step debugger through a specific dependency can re-enable debug info for one run with an environment variable — for example, `CARGO_PROFILE_DEV_PACKAGE_tokio_DEBUG=2`. The application's own debug information is never suppressed.
</Tip>

## Superseded builds

When a file changes while a rebuild is already running, `arc dev` cancels the in-flight build and starts a fresh one. You will see:

```text
  rebuilding
  superseded
  rebuilding
  app     cargo 4.21s ...
```

`superseded` means work was thrown away, not that something went wrong.

## Known issue in 0.1.3

<Warning>
`arc dev` has been observed looping `superseded` / `building` without ever serving. The cause has not been identified, and the supervisor does not report which file triggered the rebuild. Restarting `arc dev` resolves it in most cases. This fault is in the dev supervisor only — the library and request pipeline are unaffected.
</Warning>

## arc doctor

`arc doctor` checks the environment and reports anything that would prevent `arc dev` from working correctly:

```bash
arc doctor
```

It checks for Node.js on `PATH`, npm dependencies installed in the project, a valid `APP_KEY` in `.env`, and known platform-specific issues. On Windows with Microsoft Defender, it notes that the antivirus scanner adds significant time to each rebuild (the scan happens after Cargo exits and cannot be avoided with profile settings) and gives the remediation steps.

Run `arc doctor` first when `arc dev` fails in a way that is not immediately obvious.

## arc routes

`arc routes` prints the route table from the application graph:

```bash
arc routes
```

```text
GET    /           home
GET    /links/{id} links.show
POST   /links      links.store
GET    /billing    billing.index
```

Pass `--json` for machine-readable output:

```bash
arc routes --json
```

`arc routes` reads the application graph, so it requires the `uag` feature. The generated application enables it through its own `uag` feature. If `arc dev` is running in another terminal, `arc routes` reads the graph out of that process rather than building a second binary.

<Note>
`arc routes`, `arc typegen`, and `arc build` all read the application graph and are gated on the `uag` feature, the same way `arc queue` is gated on `database` + `jobs`. `cargo install arcature --features cli --locked` includes `uag` by default.
</Note>

## arc version

```bash
arc version
# arcature 0.1.3
```

The version is also readable at runtime as `arcature::FRAMEWORK_VERSION`.

## Checklist for a new project

<Steps>
  <Step title="Verify the environment">
    ```bash
    arc doctor
    ```
  </Step>
  <Step title="Start the dev server">
    ```bash
    arc dev
    ```
    Use `--port 3001` if port 1183 is taken; use `--open` to launch a browser automatically.
  </Step>
  <Step title="Inspect the route table">
    In a second terminal:
    ```bash
    arc routes
    ```
  </Step>
  <Step title="Make a code change and watch the rebuild">
    Edit any Rust file. The supervisor prints a timing line when the new binary is serving. Edit a `.vue`, `.tsx`, or `.css` file — Vite handles those without a Rust rebuild.
  </Step>
</Steps>
