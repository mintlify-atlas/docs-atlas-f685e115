Arcature applications are tested the way Tower services are tested: build the router, drive it in-process, assert on the response. There is no socket, no port to allocate, and no teardown race between test threads. The framework's own test suite uses this pattern throughout, and the same approach scales from a single-route unit test to a full application with subsystem startup.

## Driving the router

`Application::into_router` hands back the composed `axum::Router`. From there, `tower::ServiceExt::oneshot` sends a single request through the whole pipeline and returns the response.

```rust
use arcature::axum::Router;
use arcature::axum::body::Body;
use arcature::axum::http::{Request, Response};
use tower::ServiceExt as _;

async fn send(router: Router, request: Request<Body>) -> Response<Body> {
    router.oneshot(request).await.expect("infallible")
}

fn get(uri: &str) -> Request<Body> {
    Request::builder()
        .uri(uri)
        .body(Body::empty())
        .expect("request")
}
```

<Note>
`tower` is not re-exported by Arcature. A test crate using `oneshot` needs `tower = { version = "0.5", features = ["util"] }` in `[dev-dependencies]`. `axum` is re-exported as `arcature::axum`.
</Note>

This pattern exercises stages 3 through 20 of the pipeline — everything the builder composes onto the router. It does **not** exercise stages 1 and 2 (the dev proxy and the pre-routing proxy), which are composed around the router as a service in `run_with_state` and `serve`. A test that needs those has to build the service rather than the router.

## Asserting layer order

Layer order is a contract, so the framework asserts it rather than only documenting it. The technique is a marker layer that appends its own name to a response header; the resulting value spells out the order layers actually ran in. If a future edit reorders the stack, the assertion fails with a diff a reader can act on, instead of a subtly different security posture nobody notices.

If your application depends on where its own `.layer()` calls sit relative to the framework's, the same technique works. User layers are stage 21, inside everything the builder installs and outside the router.

## Route table assertions

A route table is data, so it can be asserted without a request at all:

```rust
use my_app::routes;

#[test]
fn home_route_is_registered() {
    let routes = routes::routes();
    assert_eq!(routes.url_for("home", &[]).unwrap(), "/");
}
```

`url_for` returns `Err(Error::NotFound(..))` for a name that is not in the table, so a renamed route fails the test rather than silently producing a broken link at runtime.

## Testing events

`Dispatcher::recording()` builds a dispatcher that remembers the names of the events it dispatched:

```rust
use arcature::events::Dispatcher;

let dispatcher = Dispatcher::recording();

// ... run the code under test using this dispatcher ...

assert!(dispatcher.was_dispatched("UserRegistered"));
let events = dispatcher.dispatched_events();
```

`was_dispatched(name)` and `dispatched_events()` read the record back. Both return `false` / an empty vector on a dispatcher built with `Dispatcher::new()` — recording is opt-in and costs nothing in production.

Assert on the event, not on the listener's side effect, when what you care about is that the event fired. Assert on the listener when what you care about is what it did.

## Testing mail

`Mailer::capture_ok()` accepts every message and keeps it in memory. `Mailer::capture_error()` rejects every message. Both are constructors, so a test builds one directly instead of pointing SMTP at a local catcher.

```rust
use arcature::mail::Mailer;

let mailer = Mailer::capture_ok();
// ... run the code under test ...
let sent = mailer.captured().await.expect("capturing mailer");
assert_eq!(sent.len(), 1);

let (envelope, raw_message) = &sent[0];
assert_eq!(envelope.to(), &["user@example.com".parse().unwrap()]);
```

`captured()` returns `Option<Vec<(Envelope, String)>>` — `None` when the mailer is not a capturing one, so a test that accidentally runs against real SMTP fails on the `expect` rather than passing vacuously. The `String` is the serialised message; the `Envelope` carries the actual sender and recipients, which is what you want to assert on since the envelope and the `To:` header can legitimately differ.

`capture_error()` is the test that finds bugs: it proves the calling code handles a send failure instead of unwrapping it.

## Testing job handlers

A job handler is an ordinary async function over a deserialised payload. Test it by calling the function directly:

```rust
#[tokio::test]
async fn send_welcome_email_job_delivers() {
    let mailer = Mailer::capture_ok();
    let payload = SendWelcomeEmail { user_id: 1 };

    // Call the handler directly — no queue, no worker process needed.
    send_welcome_email(payload, mailer.clone()).await.expect("job failed");

    let sent = mailer.captured().await.unwrap();
    assert_eq!(sent.len(), 1);
}
```

This covers the interesting part — the business logic and the `JobError::Retryable` / `JobError::Permanent` decision — without a database. Testing the queue itself (claim exclusivity, the `FOR UPDATE SKIP LOCKED` protocol) requires PostgreSQL and runs in the framework's own suite using a live database.

## Testing validation

`Validated<T>` and its siblings are extractors, so they are tested through a request. A `422` with an `errors` extension on the problem document is the success case for a validation test — assert on the **field names** in that extension, not on the message strings, which are not a stable interface:

```rust
let response = router
    .oneshot(
        Request::builder()
            .method("POST")
            .uri("/users")
            .header("content-type", "application/json")
            .body(Body::from(r#"{"email": "not-an-email"}"#))
            .unwrap(),
    )
    .await
    .unwrap();

assert_eq!(response.status(), 422);
let body: serde_json::Value = /* read response body */;
assert!(body["errors"]["email"].is_array());
```

## Databases in tests

There is no automatic per-test transaction rollback, but `TestDatabase::begin()` provides a `TestTransaction` that rolls back when dropped — so a test that panics leaves nothing behind. A test that needs a database connects to one named by an environment variable. The `DATABASE_URL` (or `ARCATURE_TEST_DB_URL`) environment variable provides the connection string. There is no test database provisioner; each test is responsible for its own setup and cleanup.

## The test-kit feature

`into_router` plus `oneshot` covers the router-level pipeline and needs no framework support at all — that is why this page leads with it. When a test needs the whole application — subsystem startup, state construction, the lot — `arcature::test_kit` boots one in-process and drives it as a `tower::Service`, with no socket, no port, and no teardown race.

<Note>
`test-kit` belongs only in `[dev-dependencies]`. Shipping a test harness inside a production binary is the mistake the feature split exists to prevent.

```toml
[dev-dependencies]
arcature = { version = "0.1", features = ["test-kit"] }
```
</Note>

What `test-kit` provides:

<Accordion title="TestApp and TestServer">
`TestApp` is the in-process driver. It boots the application, runs subsystem startup, and drives it as a `tower::Service` — no socket, no port.

`TestServer` binds a real socket for the few things a `tower::Service` call cannot exercise, such as a WebSocket upgrade or an SSE stream. Both are created by the `#[arcature::test(app = ...)]` macro, which binds a fresh `TestApp` to the test function's parameters.
</Accordion>

<Accordion title="TestRequest and TestResponse">
`TestRequest` is a fluent builder for requests. `TestResponse` adds assertion methods including `assert_problem`, which checks the content type is `application/problem+json`, the `type` URI, and the status in one call.
</Accordion>

<Accordion title="Session seeding with acting_as">
Behind the `auth` feature, `TestRequest::acting_as(user)` seeds a session so the request arrives already authenticated. This avoids the overhead of a full login flow in tests that are about authorisation or content, not about the login form itself.
</Accordion>

<Accordion title="Database assertions">
Behind the `database` feature, `assert_database_has` checks that a row matching a set of column values exists in a table. The two-condition gate checks both that a database is configured and that it is safe to write to.
</Accordion>

<Accordion title="Recorder fakes">
`test-kit` wires recorder fakes for events, jobs, and mail into the seams those subsystems already expose — not as parallel copies. `Dispatcher::recording()`, `Mailer::capture_ok()`, and the job recorder are the same types available outside `test-kit`; the feature just makes them easier to inject into an application that uses `run_with_state`.
</Accordion>

```rust
#[arcature::test(app = my_app::build)]
async fn creating_a_user_fires_the_welcome_event(app: TestApp) {
    let response = app
        .post("/users")
        .json(serde_json::json!({"email": "ada@example.com", "password": "hunter2"}))
        .send()
        .await;

    response.assert_status(201);
    app.assert_database_has("users", [("email", "ada@example.com")]).await;
    app.events().assert_dispatched("UserRegistered");
}
```

Nothing in `test-kit` registers anything globally — no inventory, no thread-local, no ambient application. A test names the thing it is testing and holds it in a value. Two tests running in parallel cannot interfere through shared state.
