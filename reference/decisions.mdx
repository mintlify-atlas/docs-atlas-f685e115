Some design decisions in Arcature are surprising enough to be worth writing down — not just documented, but explained with the context that made the choice, the alternatives that were considered, and the cost paid. Five decisions meet that bar. Each lives in `docs/decisions/` alongside the source code it describes, so the record is always one directory away from the code it governs.

The format follows Michael Nygard's Architecture Decision Record pattern: a decision statement, the context that forced it, and the cost paid. Where a decision references another (the CSRF cookie references the no-npm decision), the linkage is explicit.

<Accordion title="ADR 0001 — Arcature publishes no npm package">

### Decision

Arcature ships Rust and nothing else. There is no `@arcature/*` package on npm, no Vite plugin, no virtual module, no client runtime, and no CSRF shim. Applications install the official Inertia adapters (`@inertiajs/react`, `@inertiajs/vue3`, `@inertiajs/svelte`) directly.

Everything the Rust side needs to communicate to the JavaScript side travels as **generated `.ts` files written into the application's own source tree** under `resources/js/generated/`, gitignored and regenerated by `arc typegen` from the page contracts. A generated file is read by the TypeScript compiler at build time. Nothing imports an Arcature package at runtime.

### Context

The predecessor framework published `@arcature/client`: a Vite plugin, a virtual module, an action/query runtime, and a CSRF shim. Each piece existed to serve another. The plugin existed so the virtual module could exist; the virtual module existed so the runtime could be imported without a path. None of it was what an application asked for, and all of it had to be versioned in lockstep with the Rust crate across two registries with two release cadences.

The Inertia protocol requires none of it. Inertia is an HTTP contract — a header, a JSON page object, an asset version. A stock client speaks it. The only thing the predecessor's shim actually fixed was a cookie name, and a cookie name can be changed on the server (see ADR 0002).

### Cost

**Generated files live in the source tree.** A virtual module is invisible — resolved by the bundler, never appearing on disk. Generated `.ts` files appear in `resources/js/generated/`, have to be gitignored, have to be regenerated when contracts change, and will occasionally be stale when someone edits Rust and does not rerun the generator. The staleness is visible as a type error rather than silent, which is why it is the cost worth paying — but it is a real cost.

**No plugin means no bundler integration.** Arcature cannot hook Vite's module graph, so it cannot automatically invalidate generated types on save. Applications configure Vite themselves.

</Accordion>

<Accordion title="ADR 0002 — The CSRF cookie is XSRF-TOKEN, not __Host-csrf">

### Decision

`CsrfConfig::new()` — the default — issues a `__Host-csrf` cookie and expects `x-csrf-token`, with `Secure` and `SameSite=Strict`. That is the strong configuration and it stays the default.

`CsrfConfig::inertia()` issues `XSRF-TOKEN` and expects `x-xsrf-token`, with `Secure` and `SameSite=Lax`. Inertia applications use this one.

```rust
// For Inertia applications (standard choice):
.csrf(CsrfConfig::inertia())

// For API-only applications (stricter, manual JS required):
.csrf(CsrfConfig::new())
```

### Context

Inertia's client is axios. axios reads a cookie named exactly `XSRF-TOKEN` and sends it back in a header named exactly `X-XSRF-TOKEN`. Those names are not configurable in any way that survives Inertia's own use of the instance; they are what the client does.

Against `CsrfConfig::new()`, a stock Inertia form POST is rejected with 403. The application's options are to write JavaScript that reads the token and reconfigures axios, or to change the names on the server. Writing JavaScript is a client-side shim — precisely the kind of framework-owned JavaScript this project does not publish (ADR 0001), and something that would be rewritten in every project.

The server is where the names are cheap to change. The double-submit check, the safe-method exemption, the bearer-token exemption, and the constant-time comparison are identical between the two configurations. Only the cookie name and `SameSite` value differ.

### Cost

Two cookie attributes weaken, deliberately:

**No `__Host-` prefix.** The prefix mandates `Secure`, forbids `Domain`, and pins `Path=/`, preventing a sibling subdomain from overwriting the cookie. axios will not look for a prefixed name, so it goes. The exposure is an attacker who already controls a subdomain overwriting `XSRF-TOKEN` with a known value — a session-fixation-shaped attack on the nonce, not a way to read the real one. It matters only after a subdomain is already lost.

**`SameSite=Lax` rather than `Strict`.** `Strict` withholds the cookie on every cross-site navigation, including an OAuth callback and a link from email, so the first page load after one arrives without a token and the next form POST fails. `Lax` sends it on top-level GET navigations only. That is exactly the case `Strict` breaks, and it is not a case CSRF exploits: a forged unsafe request still arrives without the cookie.

An application that prefers `CsrfConfig::new()` and wants to configure axios itself can; the auth guide shows what that takes.

</Accordion>

<Accordion title="ADR 0003 — Exactly one TCP port, in development as well as production">

### Decision

An Arcature application listens on one TCP port. In production that is the application server. In development it is still the application server: Vite runs in `middlewareMode`, binds no TCP port at all, and listens on an IPC endpoint (a Unix domain socket on Linux/macOS, a Windows named pipe) that the Rust process forwards to. The browser sees one origin for the page, the assets, and the HMR WebSocket.

There is deliberately no fallback to opening port 5173. If the IPC endpoint is not there, the dev proxy is inactive and Vite requests reach the application router, which returns 404.

```text
browser --TCP:1183--> arc dev
                        |-- Vite's? --> vite IPC   (ARCATURE_VITE_IPC)
                        `-- otherwise -> app IPC
```

### Context

The conventional setup runs the frontend on one port and the backend on another. It works, and it makes development a different system from production in the ways that matter most:

- **Two origins.** Cookies are per-origin. `Secure`, `SameSite`, and `__Host-` behave differently across them, so the configuration that works in development is not the configuration that runs in production — a difference that surfaces at deploy time.
- **CORS in development only.** Preflights and credentialed requests get configured to make the split work, then have to be remembered as development-only when the split disappears.
- **A shadow routing table.** Either Vite proxies `/api` to the backend or the backend proxies assets to Vite. Either way there is a second routing table that exists nowhere in production and drifts from the real one.

One port removes all three at once by making development resemble production rather than adding configuration to paper over the gap. Vite supports this directly: in `middlewareMode` it does not create a server but hands back middleware.

`arc dev` mints two IPC endpoints at startup, starts Vite against one and the application against the other, binds the single TCP port itself, and rebuilds only the application child so the listener and HMR socket survive a save. The address is published in `.arcature/dev.addr` so `arc typegen` run from a second terminal can read the graph from the running process.

### Cost

**An unfamiliar transport.** When a TCP server misbehaves you can `curl` it. An IPC endpoint needs different tools, and a Windows named pipe needs different tools again. The failure modes are honest — connect-time `NotFound` falls through to a 404, a mid-request failure is a redacted 502 — but they are less familiar than a connection refused on port 5173.

**Vite must be started by the tooling.** A developer cannot run `npx vite` in a separate terminal and have it work, because a TCP Vite is not what the proxy forwards to. The IPC path is process-private and per-invocation.

</Accordion>

<Accordion title="ADR 0004 — Layer order is a written contract">

### Decision

The order in which Tower layers wrap the router is fixed in `src/application/pipeline.rs` and documented there as a numbered table with a justification per row. It does not follow builder call order. `.inertia()` before `.csrf()` and `.csrf()` before `.inertia()` produce the same pipeline.

The ordering is asserted by the test suite — moving Inertia, CSRF, or the timeout to the wrong side of the user layers fails the tests, not just the review.

### Context

Layer order is not a style question. It determines behaviour in ways invisible until the day they matter:

- Security headers outside the body limit means a `413` carries `nosniff` and a framing policy. Inside, it does not — and a `413` is a document a browser renders.
- The access log outside the panic catcher means a `500` is logged. Inside, the panic is caught and the line is never written.
- The session outside CSRF means the token can be looked up. The other way round, every unsafe request is rejected.
- Inertia innermost of the framework layers means a CSRF rejection is returned as itself, not dressed up as an Inertia response the client tries to render as a page.

If the order came from builder call order, every one of those would be a property of how somebody happened to write their `main`. The behaviour would be correct in the scaffold and quietly wrong the first time someone reordered the builder chain to group related calls together.

Fixing the order also makes it reviewable. A table with one reason per row is a thing a person can read and disagree with. A behaviour that emerges from call order is not written down anywhere and can only be discovered by experiment.

### Cost

**The order is not configurable.** An application that genuinely needs a layer between the session and CSRF cannot express that. `.layer()` installs user layers at one position — innermost, where the request has already been limited, timed, and authenticated. Anything else means dropping to raw Axum.

**One more place to keep true.** The table is prose beside code, and prose can rot. A change to `Pipeline::apply` that does not update the table is a defect that only a reviewer will catch.

</Accordion>

<Accordion title="ADR 0005 — There is no hidden registry">

### Decision

Arcature has no global registry. Specifically: no `inventory`, no `linkme`, no distributed slices, no life-before-main constructors, no process-wide `HashMap<TypeId, Box<dyn Any>>` service locator, and no thread-locals or task-locals holding framework state.

All framework metadata is `&'static` const data emitted by macros at the definition site and gathered by explicit code the application wrote. `module!` names its controllers, jobs, and listeners; `application!` names its modules; `PageContracts::register` is called with the contract. Nothing registers itself.

Dependency injection is `Resolve<S>`: a trait resolved at compile time against the application's own state type. There is no container to look anything up in. `deny.toml` denies `inventory`, `linkme`, and `ctor` outright, so adding one fails the build rather than relying on review.

### Context

A registry is genuinely convenient: write `#[job]` on a struct, have it appear in the worker's dispatch table, never maintain a list. The convenience is real and the costs arrive later, all at once:

- **The wiring is unreadable.** "Where is this handler registered?" has no answer in the source. The link step is the answer, and the link step is not a file anyone can open.
- **Registration is a build artifact.** A job vanishes because its module was optimised out, or because it lives in a crate nothing references. The symptom is a job that silently never runs — the failure that costs the most to diagnose.
- **Nothing can be inspected without running it.** `arc doctor` and graph validation want to answer "what does this application contain" as a side-effect-free question. A link-time registry only answers it by starting the process.
- **Tests share state.** A process-wide registry is shared by every test in the binary. The first test that registers something changes the second test's world.
- **`TypeId`-keyed containers fail at runtime.** A missing dependency in a service locator is a panic on the request that needed it, in production, at the worst moment. The same mistake against `Resolve<S>` is a compile error.

Const wiring gives up the convenience and keeps everything else. `&'static` data costs no allocation, is visible in the source where it was written, and can be walked by a tool that never starts a server. `ApplicationGraph` validates duplicates, unknown imports, and cycles from that data alone.

### Cost

**Wiring is manual and is boilerplate.** Adding a job means writing the type *and* naming it in `module!`. Forgetting the second step means the job does not run. The compiler will not tell you — the same silent failure a registry was meant to prevent, arrived at from the other direction.

**Macros do more work.** Emitting const metadata that stays in step with the types around it is harder than emitting a submission to a global slice, which is why every DSL macro carries error handling and an `ARC-M<NNN>` error code.

**No third-party extension by declaration.** A crate cannot add a route or a job to an application by depending on Arcature and declaring one. It has to export something the application names. That is the intended trade.

</Accordion>
